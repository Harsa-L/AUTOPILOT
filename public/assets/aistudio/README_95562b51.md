# AUTOPILOT --- Engineering audit for multi-protocol toy-drone control

**Audit status:** Not ready for real flight control\
**Scope:** Android application and protocol implementation only. Desktop
tooling is excluded.

> **Main conclusion:** AUTOPILOT has a reasonable architectural
> foundation, but the current protocol implementation does not yet
> justify the level of compatibility implied by the application. Several
> registered drone families use packet layouts, ports, session sequences
> and control semantics that differ from the Python references. Some of
> those differences are fundamental, not minor configuration issues.

This audit reviews the `main` branch of
[Harsa-L/AUTOPILOT](https://github.com/Harsa-L/AUTOPILOT), its
architecture documentation, protocol registry, C++ packet encoders,
native networking and video code, flight-state logic, and tests. It
compares the relevant Python protocol implementations from
[TurboDrone](https://github.com/marshallrichards/turbodrone),
[pyDroneWire](https://github.com/hakimjanov/pyDroneWire), [Maritaca E88
Controller](https://github.com/popolony2k/maritaca-e88-controller),
[E88pilot](https://github.com/Volonid/e88pilot) and other
reverse-engineering references.

**Source-access note:** The audit was also informed by the attached
`chinese toys drones.md` and `Universal_Drone_Plan_Directeur.docx`. A
separate attachment named
`Rapport UI UX application universelle pour drones Wi-Fi.md` and
separate Python attachments were not available for direct inspection in
the conversation. Python comparisons cited below refer to the linked
repositories. The attached Chinese-toy-drone README primarily documents
camera/video protocols; it does not, by itself, establish flight-control
support for every listed family.

------------------------------------------------------------------------

## 1. The most important finding: a drone family is not a protocol variant

The current application has six production protocol entries:

-   S2X
-   WiFi UAV
-   CooingDV
-   CooingDV Jieli
-   WiFi_CAM
-   X69/LG

The architecture document describes these families and their
implementation boundaries. However, the registry often represents a
whole family with one set of addresses, one packet encoder and one set
of capabilities. That is not sufficient for cheap Chinese drones.

There are several examples where the same or similar product naming
hides substantially different protocols.

### FLOW-UFO is the clearest example

The attached `chinese toys drones.md` describes a FLOW-UFO/BL60x camera
variant:

-   `FLOW-UFO-xxxxxx` or `FLOW_xxxxxx`.
-   Phone address typically `192.168.169.x`.
-   Drone address `192.168.169.1`.
-   Camera engines on UDP ports `8800` and `8801`.
-   Video replies from port `1234`.
-   Proprietary fragmented JPEG frames.
-   Periodic acknowledgements and frame requests.

That document explicitly describes a video implementation, not a
flight-control implementation. It states that no flight command is sent
by the documented application. The acknowledgements can contain a
neutral stick command in other implementations, but the documented
application leaves that field empty.

But [pyDroneWire](https://github.com/hakimjanov/pyDroneWire) describes a
different FLOW-UFO/Y-series target:

-   Control over UDP `7099`.
-   RTSP video at `192.168.1.1:7070/webcam`.
-   A 21-byte CooingDV-style command frame.
-   A 20 Hz control loop.
-   A 1 Hz heartbeat.

That is not the same connection profile as the BL60x camera path.

There is also a FLOW-WIFI/E88 variant in [Maritaca E88
Controller](https://github.com/popolony2k/maritaca-e88-controller),
which uses an 88-byte envelope containing a 20-byte inner E58 command.

Consequently, **`FLOW-` cannot be treated as a reliable protocol
identifier by itself.** It is a discovery clue, not proof of the camera
engine or flight-control protocol.

This distinction needs to be reflected in AUTOPILOT's architecture.

### 2.1 FLOW-UFO / WiFi UAV: the highest-priority problem

AUTOPILOT currently describes WiFi UAV as:

``` text
Host:          192.168.169.1
Control:       UDP 8800
Video:         UDP 8800
Heartbeat:     UDP 8800
Control frame: 8 bytes
Video:         RAW_UDP_JPEG
```

See the [AUTOPILOT WiFi UAV registry
entry](https://github.com/Harsa-L/AUTOPILOT/blob/main/drone/protocol-api/src/main/java/com/autopilot/drone/protocolapi/ProtocolCompatibilityRegistry.kt#L82-L125).

There are two important implementation problems.

**First: the flight-control frame does not match the TurboDrone WiFi-UAV
adapter.**

The current C++ encoder produces this generic format:

``` text
66 ROLL PITCH THROTTLE YAW FLAGS XOR 99
```

The TurboDrone
[`wifi_uav_rc_protocol_adapter.py`](https://github.com/marshallrichards/turbodrone/blob/main/backend/protocols/wifi_uav_rc_protocol_adapter.py)
implements an extended command format with:

-   A proprietary header.
-   Three rolling counters.
-   A command structure.
-   Axis mapping that depends on the variant.
-   Speed scaling.
-   Additional framing and checksum information.

Its constructed command is substantially longer than eight bytes.
AUTOPILOT's tests currently assert that WiFi UAV produces an eight-byte
frame. That test confirms the implementation's assumption; it does not
confirm compatibility with the reference protocol.

**Second: the video transport is not implemented.**

The attached README describes FLOW-UFO video as fragmented JPEG data
without normal JPEG headers. Fragments must be assembled, JPEG headers
reconstructed, acknowledgements generated, and subsequent frames
requested.

TurboDrone's
[`wifi_uav_video_protocol.py`](https://github.com/marshallrichards/turbodrone/blob/main/backend/protocols/wifi_uav_video_protocol.py)
gives further detail:

-   Proprietary packets beginning with `0x93`.
-   A 56-byte proprietary header.
-   Frame and fragment identifiers.
-   Fragment counts and frame lengths.
-   Frame reconstruction and JPEG-header generation.
-   REQUEST_A and REQUEST_B acknowledgements.
-   Retry and timeout handling.
-   Optional probing of both `8800` and `8801`.

Its [WiFi-UAV packet
helper](https://github.com/marshallrichards/turbodrone/blob/main/backend/utils/wifi_uav_packets.py)
also shows that the acknowledgement/request packets carry a neutral
extended command and quality parameters.

AUTOPILOT's
[VideoReassembler](https://github.com/Harsa-L/AUTOPILOT/blob/main/native/core/src/main/cpp/processing/video_reassembler.cpp)
handles several generic video formats, but its `RAW_UDP_JPEG` path looks
for normal JPEG SOI and EOI markers. It does not implement the FLOW-UFO
fragment protocol.

**Critical:** The current WiFi-UAV profile is not a complete
implementation of the documented FLOW-UFO video protocol or the
TurboDrone flight-control protocol.

For the first target, create a distinct `FLOW_BL60X` profile instead of
treating every FLOW-labelled device as the same WiFi-UAV implementation.

### 2.2 KY UFO / CooingDV: one family, at least two control variants

AUTOPILOT currently uses an eight-byte frame for CooingDV, sharing its
encoder structure with WiFi UAV.

The TurboDrone
[`cooingdv_rc_protocol_adapter.py`](https://github.com/marshallrichards/turbodrone/blob/main/backend/protocols/cooingdv_rc_protocol_adapter.py)
explicitly distinguishes two variants:

**TC variant**

-   9-byte frame.
-   `03 66` prefix.
-   Four axis bytes.
-   One command-flags byte.
-   Checksum and `99` footer.

**GL variant**

-   21-byte frame.
-   `03 66 14` prefix.
-   Four axis bytes.
-   Two command-flags bytes.
-   Extended framing and checksum.

The adapter listens for UDP telemetry and identifies the variant using
received device information. It then selects the corresponding encoder.

The flag assignments are also different from AUTOPILOT's shared mapping.
For example, the TC implementation uses `0x80` for calibration and
`0x08` for flip, whereas AUTOPILOT's generic mapping assigns those
functions differently.

That is dangerous because a packet can be structurally valid and still
request the wrong operation.

**Heartbeat timing is another mismatch.**

The attached documentation says that the KY UFO RTSP application sends:

``` text
01 01
```

to UDP `7099` once per second. It explicitly describes this as the only
traffic sent to that port by its video-only implementation.

The TurboDrone CooingDV flight adapter also sends this heartbeat at
one-second intervals, alongside its separate RC command stream.

AUTOPILOT's native worker, however, sends its generic heartbeat every
five control-loop ticks. At 25 Hz, that means approximately every 200
ms. It also transmits the generic control frame every 40 ms.

Those two operations should not be conflated.

The [CooingDV registry
entry](https://github.com/Harsa-L/AUTOPILOT/blob/main/drone/protocol-api/src/main/java/com/autopilot/drone/protocolapi/ProtocolCompatibilityRegistry.kt#L135-L180)
also omits the documented `FLY-UFO-` SSID prefix. This can prevent the
expected KY UFO profile from being detected automatically.

There is a further issue: the [pyDroneWire
controller](https://github.com/hakimjanov/pyDroneWire/blob/main/drone_controller.py)
describes a 21-byte CooingDV control frame for its FLOW-UFO/Y-series
target. That provides another reason to model it as a separate variant
rather than a generic `FLOW-UFO` alias.

**Recommended profiles:**

``` text
COOINGDV_TC
COOINGDV_GL
FLOW_KY_Y_SERIES
```

They can share reusable transport and video components, but their
command encoders should remain separate.

### 2.3 Jieli / HF: the current profile appears to mix two different implementations

Your attached documentation describes the Jieli/HF AC79 camera family
as:

``` text
Drone IP:          192.168.80.1
Control:           TCP 3333
Video receive:     UDP 6666 or 2224
Additional port:   UDP 1234 (diagnostic/audio)
Flight commands:   UDP 3456 in the vendor application
```

The CTP protocol is not a simple fixed-length binary wrapper. Messages
contain:

``` text
CTP:
topic length
topic
JSON length
JSON
```

The documented session includes `APP_ACCESS`, `KEEP_ALIVE_INTERVAL`,
`VIDEO_PARAM`, `DATE_TIME`, `CTP_KEEP_ALIVE`, `OPEN_RT_STREAM` and
`CLOSE_RT_STREAM`.

The attached README explicitly says that its implementation does not
send flight commands: no `FLIGHT_CONTROL` over CTP and nothing to the
flight-control UDP port `3456`.

AUTOPILOT's Jieli registry currently uses:

``` text
192.168.1.1
TCP 3333
Video port 2222
RTP_JPEG
```

Its C++ encoder constructs a 14-byte `CTP:`-prefixed packet, but it does
not construct the documented CTP topic-and-JSON envelope.

See the [Jieli
registry](https://github.com/Harsa-L/AUTOPILOT/blob/main/drone/protocol-api/src/main/java/com/autopilot/drone/protocolapi/ProtocolCompatibilityRegistry.kt#L188-L230)
and [native packet
encoder](https://github.com/Harsa-L/AUTOPILOT/blob/main/native/core/src/main/cpp/protocol/protocol_packets.cpp#L98-L118).

There is a second complication: TurboDrone's `cooingdv_jieli`
implementation uses a different device path, with UDP control at
`192.168.8.15:2228` and CTP messages containing JSON topics such as
`CONTROL_MODE` and `FLYING_CTRL`.

That is not the same as the AC79/HF camera path in the attached README.

**Separate these into independent implementations:**

-   `JIELI_AC79_CTP_TCP_CAMERA` --- initially video/session
    functionality only.
-   `COOINGDV_JIELI_UDP_CONTROL` --- only for the separate device
    variant verified against TurboDrone or an equivalent capture.

Do not infer flight-control support from the fact that both use the
Jieli name.

### 2.4 Lewei: not implemented

The attached README documents the Lewei camera protocol:

-   TCP port `7060`.
-   A 46-byte message header.
-   H.264 video in Annex B format.
-   A 32-byte frame header.
-   A keepalive request every second.
-   A reconnect attempt after five seconds without video.

It explicitly says that the documented application does not send flight
commands. The vendor application has a separate flight-control UDP
channel, but the attached documentation does not establish its command
format.

AUTOPILOT does not currently have a Lewei protocol family or encoder.

**Recommendation:** implement Lewei video independently when needed, but
keep its flight-control support disabled until a valid command capture
or an independently verified controller is available.

### 2.5 S2X, WiFi_CAM and X69/LG also need correction

These families are outside the four primary camera families in
`chinese toys drones.md`, but they are important to AUTOPILOT's wider
compatibility goal.

**S2X**

AUTOPILOT uses port `40000` and an 11-byte frame.

TurboDrone's
[`s2x_rc_protocol_adapter.py`](https://github.com/marshallrichards/turbodrone/blob/main/backend/protocols/s2x_rc_protocol_adapter.py)
constructs a 20-byte frame and defaults to control port `8080`. Its
video adapter uses control port `8080` and video port `8888`.

This needs reconciliation against the specific S20/S29 hardware you
intend to support.

**WiFi_CAM**

AUTOPILOT uses `192.168.4.1:50000` and an eight-byte `FF 08` command
frame.

TurboDrone's
[`wifi_cam_rc_protocol_adapter.py`](https://github.com/marshallrichards/turbodrone/blob/main/backend/protocols/wifi_cam_rc_protocol_adapter.py)
describes short and extended control modes, with different command
structures. The reference implementation defaults to
`192.168.4.153:8090`.

The Maritaca project adds another relevant detail: some WIFI_8K\_ drones
require a mode-activation packet `42 76` on UDP `8080` before flight
control works. Its documented command protocol also uses a different
eight-byte frame and an extended command mode.

AUTOPILOT's `FF 08` packet should not be considered compatible merely
because it has the expected number of axes.

**X69/LG**

AUTOPILOT currently encodes a direct 10-byte command frame and targets
port `1234`.

TurboDrone's
[`x69_lg_rc_protocol_adapter.py`](https://github.com/marshallrichards/turbodrone/blob/main/backend/protocols/x69_lg_rc_protocol_adapter.py)
instead constructs a 20-byte payload and wraps it with:

``` text
CA 47 D5 00
payload length
20-byte control payload
```

It uses UDP control port `23458` and sends a separate `D1` keepalive
approximately once per second.

The corresponding video adapter uses a different control port, `23459`,
and reconstructs H.265 frames from a proprietary 32-byte header.
AUTOPILOT's generic H.265 path does not implement that complete packet
assembly.

The current X69 profile is therefore not a faithful port of this
TurboDrone implementation.

## 3. Critical AUTOPILOT internals

The protocol discrepancies are important, but there are also problems in
the application architecture itself.

### 3.1 Automatic detection can select the wrong protocol

This is a direct bug.

The registry lists S2X before WiFi UAV. The S2X entry includes this SSID
hint:

``` text
FLOW-
```

The WiFi UAV entry does not include the exact documented prefix
`FLOW-UFO-`.

`AutopilotViewModel.detectedProtocolFromWifi()` returns the first
matching entry. Consequently, `FLOW-UFO-xxxxxx` can match S2X before the
intended WiFi-UAV family is considered.

There is a second bug in `bindWifiApForSelectedProtocol()`: it uses the
first SSID hint from the selected profile instead of the actual detected
SSID. For S2X that first hint is `Vison-`. Thus, a `FLOW-UFO-` network
can be misclassified as S2X and then the binding request can search for
a `Vison-` network.

Relevant code:

-   [ProtocolCompatibilityRegistry.kt](https://github.com/Harsa-L/AUTOPILOT/blob/main/drone/protocol-api/src/main/java/com/autopilot/drone/protocolapi/ProtocolCompatibilityRegistry.kt#L20-L105)
-   [AutopilotViewModel.kt](https://github.com/Harsa-L/AUTOPILOT/blob/main/app/src/main/java/com/example/ui/AutopilotViewModel.kt#L303-L320)
-   [WifiConnectivityController.kt](https://github.com/Harsa-L/AUTOPILOT/blob/main/drone/protocols/src/main/java/com/autopilot/drone/protocols/WifiConnectivityController.kt#L96-L150)

The detector needs to produce a list of candidates with evidence, not
return the first prefix match.

SSID, gateway and subnet should be combined with non-flight protocol
identification. The result should carry a confidence level and
unresolved alternatives.

### 3.2 AUTOPILOT starts transmitting control frames immediately after connection

**Critical safety issue**

`NativeDroneProtocolAdapter.connect()` starts the native session and
marks the connection as `Connected` once the native worker starts.

The native worker then continuously calls `encode_control_packet()` and
transmits the result at the configured control rate.

This happens even before the pilot explicitly arms the drone.

In other words, the native communication loop does not currently
distinguish:

-   Establishing a video session.
-   Sending a keepalive.
-   Sending an acknowledgement required by a video protocol.
-   Sending a neutral RC frame.
-   Sending actual pilot input.

These are different operations and must have different authorization
rules.

A neutral stick packet is still a control packet. Depending on the
drone, it can activate or maintain a control session and interfere with
another controller.

The project director says that discovery must not send flight commands.
The current native worker does not enforce that separation.

Relevant code:

-   [NativeDroneProtocolAdapter.kt](https://github.com/Harsa-L/AUTOPILOT/blob/main/drone/protocols/src/main/java/com/autopilot/drone/protocols/NativeDroneProtocolAdapter.kt#L45-L120)
-   [native_session.cpp](https://github.com/Harsa-L/AUTOPILOT/blob/main/native/core/src/main/cpp/communication/native_session.cpp#L720-L850)

**Required change:** the native session must have separate
control-transmission states. Starting a video session must not
automatically start an RC transmission loop. Only the specific
protocol-required discovery, heartbeat or video acknowledgement traffic
should be allowed before explicit control authorization.

The control loop should become active only after:

1.  The device variant is identified sufficiently.
2.  The control adapter is validated for that variant.
3.  The operator explicitly arms the control session.
4.  The protocol-specific startup sequence succeeds.

Video-only profiles must not expose or transmit flight commands.

### 3.3 `Connected` currently means that sockets started, not that the aircraft responded

The native session can start successfully because its local sockets were
opened and its worker thread was created.

`NativeDroneProtocolAdapter` then sets `ConnectionState.Connected`.

`FlightStateController` interprets this as `FlightState.Ready`.

That means the UI can become ready for flight without evidence that the
drone received a handshake, acknowledged a command, returned telemetry
or even exists at the configured address.

The watchdog has another weakness: it only declares a timeout if the
session has already received at least one packet. If no response ever
arrives, that condition remains false and the watchdog does not report
the absence of a working link.

Additionally, the native session counts inbound packets from video and
telemetry sockets together. A live video stream can therefore keep the
generic packet counter active without proving that the control channel
is healthy.

See
[FlightStateController.kt](https://github.com/Harsa-L/AUTOPILOT/blob/main/flight/control/src/main/java/com/autopilot/flight/control/FlightStateController.kt#L175-L205)
and
[native_session.cpp](https://github.com/Harsa-L/AUTOPILOT/blob/main/native/core/src/main/cpp/communication/native_session.cpp#L820-L850).

I recommend separating these states:

  -----------------------------------------------------------------------
  State                               Meaning
  ----------------------------------- -----------------------------------
  `WifiConnected`                     Android is connected to the drone
                                      AP

  `SessionStarting`                   The selected protocol's startup
                                      sequence is underway

  `ProtocolDetected`                  There is evidence of the selected
                                      protocol

  `VideoReady`                        The video transport is receiving
                                      valid frames

  `ControlLinkReady`                  The control channel has received
                                      valid protocol-specific evidence

  `Armed`                             The operator has explicitly
                                      authorized flight control

  `Flying`                            Flight has been confirmed by
                                      reliable telemetry, if available

  `LinkLost`                          The relevant control or video
                                      channel has exceeded its own
                                      timeout
  -----------------------------------------------------------------------

A video connection must not automatically imply flight readiness.

### 3.4 Flight-state transitions are optimistic

`FlightStateController.takeoff()` sends the takeoff command and then
changes the state to `Flying` after 600 ms.

`controlledLand()` changes the state to `Ready` after 800 ms unless the
optional soft-descent routine is enabled.

Those timers represent application assumptions, not observed aircraft
state.

A command being transmitted does not prove that the drone accepted it or
completed the requested action.

The same issue applies to the generic `arm()` process. It can set the
application to `Armed` based on local state even when no confirmed
control-link response exists.

This should be changed so that application state reflects what the
protocol can actually verify. For protocols without telemetry, the UI
should clearly identify the state as *command issued*, *unconfirmed* or
*estimated*, rather than presenting it as verified flight state.

### 3.5 Capability flags are too generous

The registry advertises capabilities such as:

-   Takeoff.
-   Controlled landing.
-   Emergency motor stop.
-   Gyroscope calibration.
-   Headless mode.
-   Flip.
-   Unlock motors.
-   Fast fly.
-   Firmware photo and recording.

Many of these are enabled on profiles that are still marked
`IMPLEMENTED_UNVERIFIED` or `EXPERIMENTAL`.

The application currently has a generic flag mapping in
[protocol_packets.cpp](https://github.com/Harsa-L/AUTOPILOT/blob/main/native/core/src/main/cpp/protocol/protocol_packets.cpp#L20-L150).
That assumes that the same semantic command has the same bit position
across protocols.

The CooingDV example already proves otherwise.

**The capabilities should be declared by exact device variant, backed by
evidence, and gated by verification status.** A family being known does
not mean every action is supported.

In particular, an emergency motor stop should never be enabled simply
because the adapter has an `EmergencyStop` command in its interface. On
some aircraft, cutting the motors causes an immediate fall. The
semantics need to be documented and tested for each actual device.

### 3.6 Android network binding must fail safely

`open_bound_udp_socket()` and `open_bound_tcp_socket()` attempt to
associate sockets with the selected Android network using
`android_setsocknetwork()`.

If that operation fails, the code records the error but still returns
the socket.

That is not a safe failure mode for a drone network. The application may
continue transmitting through a socket that is not bound to the intended
access point.

The app should fail the session or explicitly report that network
binding has not been established. It must not silently continue and then
present a healthy connection.

## 4. The current abstraction is not yet sufficient for universal compatibility

The architecture document correctly separates protocol, video, vision,
tracking, flight and UI modules. That is a good direction. The weakness
is in the protocol model itself.

At the moment, the principal abstraction is effectively:

``` text
ProtocolFamily
    ├── control port
    ├── video port
    ├── heartbeat port
    ├── video transport
    └── capabilities
```

For universal toy-drone support, that is too limited.

I would introduce an explicit **DeviceProfile + ProtocolVariant** model.

### Recommended profile structure

``` text
DeviceProfile
├── identity
│   ├── profileId
│   ├── manufacturerFamily
│   ├── modelNames
│   ├── firmwareVariants
│   └── evidence
│
├── discovery
│   ├── ssidPatterns
│   ├── gatewayHints
│   ├── subnetHints
│   ├── identificationProbes
│   └── confidenceRules
│
├── channels
│   ├── controlChannel
│   ├── videoChannel
│   ├── telemetryChannel
│   ├── heartbeatChannel
│   └── localBindRequirements
│
├── session
│   ├── startupSequence
│   ├── handshake
│   ├── heartbeatPolicy
│   ├── reconnectPolicy
│   └── shutdownSequence
│
├── control
│   ├── packetEncoder
│   ├── axisMapping
│   ├── axisRange
│   ├── centerValues
│   ├── controlFrequency
│   ├── discreteCommands
│   └── failsafePolicy
│
├── video
│   ├── transport
│   ├── packetParser
│   ├── frameReassembler
│   ├── codec
│   ├── orientation
│   └── frameRequestPolicy
│
└── capabilities
    ├── verifiedCommands
    ├── unverifiedCommands
    ├── unavailableCommands
    └── hardwareEvidence
```

The key idea is that a brand or family can contain several device
profiles.

For example:

``` text
FLOW_UFO
├── FLOW_BL60X
│   ├── BL608
│   └── BL618
│
├── FLOW_KY_Y_SERIES
│   └── CooingDV-compatible control
│
└── FLOW_WIFI_E58
    └── Extended E58 command envelope
```

This will avoid the current problem of choosing one packet format for
every drone whose SSID begins with the same word.

### Separate control from video

A drone may expose a camera protocol without exposing a documented
flight-control protocol.

Likewise, a drone could expose a flight-control channel while its camera
uses an incompatible proprietary stream.

The system should therefore allow:

``` text
DroneSession
├── ConnectivitySession
├── ProtocolIdentificationSession
├── VideoSession
├── ControlSession
└── TelemetrySession
```

Each session should have an independent status and timeout.

A video-only device profile should be a legitimate profile, not an
incomplete flight controller.

------------------------------------------------------------------------

## 5. What I would implement first

The priority should be to make a small number of profiles genuinely
correct, then expand.

### P0 --- Fix safety and protocol identification

**Do this before flight testing.**

Disable generic flight transmission during connection and video-only
sessions. Separate the heartbeat from the RC loop. Correct the SSID
matching and binding logic. Make `Connected` distinct from
`ControlLinkReady`, and prevent unverified capabilities from enabling
commands.

### P1 --- FLOW-UFO / BL60x

**Best first target for the documented D16.**

Implement a dedicated BL60x video adapter: probe `8800` and `8801` as
required, identify which responds, parse the proprietary `0x93`
fragments, reconstruct JPEG frames, maintain ACK state, request
subsequent frames and restart discovery after a stalled stream.

Do not enable flight control for this profile merely because video
works. First establish the exact flight packet sequence from the
relevant physical drone's vendor-app traffic or another reliable
hardware-verified implementation.

### P2 --- KY UFO / CooingDV

Implement the RTSP camera path and its one-second heartbeat separately
from the flight-control adapter. Add TC and GL variant detection using
received telemetry. Implement and test each control frame independently.
Add a separate profile for the KY Y-series variant documented by
pyDroneWire if the hardware evidence matches.

### P3 --- E88 / WiFi_CAM variants

Use the E88pilot and Maritaca references to build distinct E88/E58
profiles. Support mode activation when required, exact local and remote
UDP ports, short/extended command encoders, and the correct keepalive
policy.

### P4 --- Jieli and Lewei

Implement the AC79/HF video session as its own CTP/TCP path. Keep its
flight-control support disabled until the corresponding flight-control
protocol has been independently verified. Add Lewei TCP video
separately; do not advertise flight support without evidence.

### P5 --- S2X and X69/LG

Reconcile ports, command packet layouts, startup sequences and video
framing against the exact TurboDrone references and physical captures.
Keep these profiles experimental until then.

## 6. Tests AUTOPILOT needs before claiming compatibility

The existing
[ProtocolPacketEncoderTest.kt](https://github.com/Harsa-L/AUTOPILOT/blob/main/drone/protocols/src/test/java/com/autopilot/drone/protocols/ProtocolPacketEncoderTest.kt#L16-L190)
is useful as a starting point, but it currently validates assumptions
such as the generic eight-byte WiFi-UAV and CooingDV frames.

A checksum being correct does not mean that the packet matches the
drone.

I would require the following test layers.

  -----------------------------------------------------------------------
  Test layer                          What it must verify
  ----------------------------------- -----------------------------------
  Golden packet fixtures              Exact bytes from known captures,
                                      including counters, headers, flags
                                      and checksums

  Protocol encoder tests              Each device variant, not just each
                                      broad family

  Session-sequence tests              Correct ordering of startup,
                                      handshake, heartbeat, control and
                                      shutdown

  Timing tests                        Control and heartbeat frequencies,
                                      including timeout and retry
                                      behaviour

  Network tests                       Correct local source ports, remote
                                      addresses and network binding

  Video parser tests                  Fragment ordering, missing
                                      fragments, duplicates, retries, bad
                                      headers and frame timeouts

  Safety tests                        No RC commands before explicit
                                      authorization, and no flight
                                      capability on video-only profiles

  Hardware tests                      Real connection and controlled
                                      flight tests for each supported
                                      model and variant
  -----------------------------------------------------------------------

I would also introduce replayable packet captures as first-class test
fixtures. Every protocol added to AUTOPILOT should have at least one
known capture for connection and video, and separate flight-control
evidence before its flight capabilities are enabled.

The current repository documentation itself acknowledges that real
hardware verification was not carried out in the cloud environment. That
is an important limitation to preserve in the application rather than
hiding it behind a status such as `IMPLEMENTED`. See
[docs/ARCHITECTURE.md](https://github.com/Harsa-L/AUTOPILOT/blob/main/docs/ARCHITECTURE.md#L39-L75).

## 7. Final assessment

### What AUTOPILOT already has going for it

-   A native Android architecture with Kotlin, Compose, C++20 and JNI.
-   A separation between the protocol layer, video pipeline, vision and
    flight control.
-   A useful protocol registry and a unified command model.
-   A native video reassembly path for several standard formats.
-   A meaningful starting point for connection diagnostics and
    telemetry.

### What prevents it from being a reliable universal toy-drone controller

-   Broad family names are being used where exact device variants are
    required.
-   Some packet encoders do not match the corresponding Python
    references.
-   FLOW-UFO proprietary video framing and acknowledgement handling are
    missing.
-   CooingDV TC/GL variants are not represented correctly.
-   Jieli profiles mix different device paths and use an incomplete CTP
    frame.
-   Several registered capabilities are not substantiated by hardware
    evidence.
-   Control packets are transmitted before explicit arming.
-   Connection and flight states are optimistic rather than based on
    protocol evidence.
-   The tests validate the current encoders, not necessarily the actual
    drone protocols.

**My recommendation is not to discard the current AUTOPILOT
architecture.** Keep the native session infrastructure, the unified
flight-input model and the video pipeline, but make the protocol layer
genuinely variant-based and evidence-driven.

The product goal should be:

> AUTOPILOT can support any toy drone for which a compatible protocol
> profile can be identified, implemented and verified, while safely
> handling unknown drones without sending unverified flight commands.

That is a much stronger engineering target than supporting a fixed list
of six broad protocol names.

For the first milestone, focus on **a correct FLOW-UFO/BL60x video
implementation and a separate, independently verified flight-control
profile**. This establishes the foundation for the rest of the cheap
Wi-Fi drone families without confusing camera compatibility with flight
compatibility.
